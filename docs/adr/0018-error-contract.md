# ADR 0018: Error contract, status mapping and correlation id

Status: Proposed · Date: 2026-11-14 · Amends 0004

## Context
Review findings B-6, B-8; audit findings R-12, R-13. Checked against `error.proto` and
`ledger_service.proto`:
- `correlation_id` is a field of every request and response. In the generated OpenAPI it becomes a query
  parameter on every GET.
- There is no code for lock contention or for a dependency being down; both would surface as `INTERNAL`.
- `ledger.v1.ErrorInfo` shares its simple name with `google.rpc.ErrorInfo`.
- `DUPLICATE_IDEMPOTENCY_KEY_CONFLICT` is `ABORTED` / 409. The review adds `CONTENTION` as `ABORTED` too.
- `FAILED_PRECONDITION` codes promise 422.

`google/rpc/code.proto` (verified, googleapis master, read 2026-11-14): `ABORTED` is "typically due to a
concurrency issue such as a sequencer check failure or transaction abort"; the guideline says "use `ABORTED`
if the client should retry at a higher level", "use `UNAVAILABLE` if the client can retry just the failing
call", "use `FAILED_PRECONDITION` if the client should not retry until the system state has been explicitly
fixed". `ALREADY_EXISTS`: "the entity that a client attempted to create already exists". HTTP: `ABORTED` and
`ALREADY_EXISTS` 409, `FAILED_PRECONDITION` and `INVALID_ARGUMENT` 400, `UNAVAILABLE` 503,
`RESOURCE_EXHAUSTED` 429.

## Decision
1. **Shape.** gRPC: `google.rpc.Status` with one `ledger.v1.LedgerErrorDetail` in `details` (renamed from
   `ErrorInfo`). REST: the same `Status` as JSON. `RATE_LIMITED` and `CONTENTION` may add a standard
   `google.rpc.RetryInfo`.
2. `LedgerErrorDetail`: `code`, `message` (operator text, not stable), `correlation_id`, `request_id`,
   `field_violations`. Never stack traces, SQL, account ids of other requests, or values of the request.
3. **Correlation id is a header**: `x-correlation-id` (HTTP header and gRPC metadata). 1–128 characters from
   `[A-Za-z0-9._:-]`. Absent or invalid → the server generates one; an invalid value is dropped, not logged.
   It is echoed in the response header and in `LedgerErrorDetail`. The field leaves every request and response
   message.
4. **Request id**: generated by the server for every request, returned as `x-request-id` and in the detail.
   A client-sent `x-request-id` is ignored.
5. **Mapping.** One table, below. "Recorded" means the rejection is stored under the idempotency key and
   replayed (ADR 0017). Codes 17–24 are new.

| # | Code | gRPC | HTTP | Recorded | Caller action |

| 2 | INVALID_ENTRY | INVALID_ARGUMENT | 400 | no | fix request |

6. `PERMISSION_DENIED` covers a missing scope, an unregistered or suspended tenant (ADR 0023) and the
   overdraft scope (ADR 0024). The message does not say which.
7. **Responses that may lack `LedgerErrorDetail`** (R-13). Clients must fall back to the status code:
   - anything produced outside the service: proxies, load balancers, TLS failures, connection resets;
   - gRPC statuses generated by the library or the client: `UNIMPLEMENTED` (unknown method),
     `RESOURCE_EXHAUSTED` (message larger than the limit), `DEADLINE_EXCEEDED`, `CANCELLED`;
   - REST errors raised by the framework before the adapter: unknown path (404), method (405), media type
     (415), body too large (413). The adapter attaches a detail where the framework lets it; a test lists
     which ones it covers.
8. `ErrorCode` values are only appended. Clients must treat an unknown value as "failed, not retryable unless
   the status is `UNAVAILABLE`, `ABORTED` or `RESOURCE_EXHAUSTED`" (ADR 0032).

## Consequences
- `ABORTED` now always means "retry the same call with the same key". Conflict no longer shares it, so a
  generic retry policy on `ABORTED` cannot loop on a conflict.
- Client retry policies must include `ABORTED` for ledger writes. This is safe because every write carries a
  key.
- Every write and every rejection carries `request_id` and `correlation_id` for the audit trail (ADR 0013).
- Proto follow-up: rename the message, add codes 17–24, change the status comments, remove `correlation_id`
  fields, regenerate OpenAPI.

## Alternatives rejected
- **`CONTENTION` as `UNAVAILABLE` / 503.** Matches guideline (a) word for word, since the client retries the
  same call. Rejected because 5xx on a hot account looks like an outage: proxies that eject hosts on
  consecutive 5xx would remove healthy instances (depends on proxy configuration; unverified for any
  specific proxy). `ABORTED`'s own text names "transaction abort".
- **Conflict stays `ABORTED` (current draft).** Under guideline (b) a client restarts and sends the same key
  again, and gets the same conflict.
- **`UNBALANCED_ENTRY` stays `FAILED_PRECONDITION`.** It does not depend on system state; guideline (c) does
  not apply.
- **`OUT_OF_RANGE` for `BALANCE_LIMIT_EXCEEDED`.** Its text is about iterating past an end; it would mislead.
- **Reject an invalid correlation id.** A tracing header should not fail a money write.

## Relation to the review and the audit
Agrees with B-6 and B-8 (rename, `CONTENTION`, `UNAVAILABLE`). **Differs**: conflict moves to
`ALREADY_EXISTS` (accepts R-12), `UNBALANCED_ENTRY` moves to `INVALID_ARGUMENT`, and the "recorded" column
follows ADR 0017. Accepts R-13 for the list of detail-less errors.
