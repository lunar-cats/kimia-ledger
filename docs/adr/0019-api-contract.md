# ADR 0019: API contract: REST conforms to the transcoding mapping, error contract, contract freeze and breaking baseline

Status: Proposed · Date: 2026-11-15 · Amends 0004, 0012

Replaces earlier drafts: old 0015, old 0018, old 0032 (all first written 2026-11-14).

## Context
Review findings B-2, B-6, B-8, B-10; audit findings R-12, R-13; review §13. ADR 0004 says REST *is* gRPC-JSON
transcoding and lists a "transcoding runtime"; `CLAUDE.md` describes `ledger-api-rest` as hand-written; no runtime
was ever chosen. Checked on 2026-11-14:
- Spring gRPC has no transcoding; the feature request (spring-projects/spring-grpc, issue 339) is open, with no
  milestone and no maintainer commitment (per the review; not re-checked here).
- `google/rpc/code.proto` (verified, googleapis master, read 2026-11-14): `ABORTED` is "typically due to a
  concurrency issue such as a sequencer check failure or transaction abort"; "use `ABORTED` if the client should
  retry at a higher level", "use `UNAVAILABLE` if the client can retry just the failing call", "use
  `FAILED_PRECONDITION` if the client should not retry until the system state has been explicitly fixed".
  `ALREADY_EXISTS`: "the entity that a client attempted to create already exists". HTTP: `ABORTED` and
  `ALREADY_EXISTS` 409, `FAILED_PRECONDITION` and `INVALID_ARGUMENT` 400, `UNAVAILABLE` 503,
  `RESOURCE_EXHAUSTED` 429.
- The draft `error.proto` documented 422; `correlation_id` was a field of every message (a query parameter on
  every GET in OpenAPI); there was no code for contention or for a dependency being down; `ledger.v1.ErrorInfo`
  shared its name with `google.rpc.ErrorInfo`; ADR 0004 gave the proto path as `contracts/ledger/v1/`, the files
  are in `contracts/proto/ledger/v1/` (S-4).
- `buf breaking` compares against `main`, so every review fix would count as breaking once the draft merges.
  Protobuf JSON parsers commonly reject an unknown enum name or field unless configured (Java and C# behaviour:
  unverified, human to confirm with the first consumer).

## Decision

### D1. REST is a hand-written adapter that conforms to the transcoding mapping (old 0015)
1. The protos with their `google.api.http` options stay the **only definition** of the REST surface; OpenAPI
   stays generated. REST and gRPC are both first-class in v1 (owner baseline).
2. `ledger-api-rest` is a **hand-written Spring MVC adapter**. No transcoding runtime, proxy or library is in the
   request path. For every `google.api.http` binding it serves the same method, path, path variables, query
   parameters and body.
3. Bodies are the generated proto messages, parsed and printed with protobuf's own JSON mapping. No hand-written
   DTOs; no second JSON mapping for money.
4. A request with a field the server does not know → `INVALID_ARGUMENT`, on REST and gRPC. A ledger must not drop
   a field the caller meant. (Clients, by contrast, must tolerate unknown fields: D3.5.)
5. Errors are the `google.rpc.Status` JSON shape (D2). HTTP status is the standard `google.rpc.Code` mapping;
   **422 leaves the contract**; the codes that documented it return 400.
6. New paths use sub-resources, not the `:verb` suffix (for example `POST /v1/transactions/{transaction_id}/reversal`;
   full list review §13.1).
7. A conformance test reads the proto descriptors and fails if a binding is not served; a second test sends the
   same request over REST and gRPC and compares the responses.

### D2. Error contract, status mapping and correlation id (old 0018)
1. **Shape.** gRPC: `google.rpc.Status` with one `ledger.v1.LedgerErrorDetail` in `details` (renamed from
   `ErrorInfo`); REST: the same `Status` as JSON. `RATE_LIMITED` and `CONTENTION` may add `google.rpc.RetryInfo`.
2. `LedgerErrorDetail`: `code`, `message` (operator text, not stable), `correlation_id`, `request_id`,
   `field_violations`. Never stack traces, SQL, ids of other requests, or values of the request.
3. **Correlation id is a header**, `x-correlation-id` (HTTP and gRPC metadata), 1–128 characters from
   `[A-Za-z0-9._:-]`. Absent or invalid → the server generates one; an invalid value is dropped, not logged.
   Echoed in the response header and in the detail. The field leaves every message.
4. **Request id**: generated by the server for every request, returned as `x-request-id` and in the detail. A
   client-sent `x-request-id` is ignored.
5. **Mapping.** "Recorded" = stored under the idempotency key and replayed (ADR 0018 D3). Rows 17–24 were new in
   this ADR.

`INVALID_ENTRY`, `UNBALANCED_ENTRY` and `TOO_MANY_POSTINGS` keep the word ENTRY on purpose: it means a double-entry
set of postings, and the same names appear in invariants I-1, I-2, I-4 and I-22. The draft `error.proto` uses the old names
for rows 6, 7, 8, 10 and 11 (`ERROR_CODE_CURRENCY_MISMATCH`, `ERROR_CODE_ACCOUNT_NOT_FOUND`,
`ERROR_CODE_ACCOUNT_CLOSED`, `ERROR_CODE_ENTRY_NOT_FOUND`, `ERROR_CODE_ENTRY_ALREADY_REVERSED`) and has no value for
row 20 yet. These names are renamed when the protos are rewritten, which the draft status until `v1.0.0` (D3.1)
allows. `buf breaking` reports each rename (verified with buf 1.75.0: `Enum value "7" on enum "ErrorCode" changed
name`); before `v1.0.0` it does not block.

6. **Additions** (values appended; status and recorded flag in review §13.3): wallet and bucket codes and
   `APPROVAL_REQUIRED` (ADR 0021 D4, D5); account-state codes (ADR 0022 D7); hold codes (ADR 0023 D4); FX and
   settlement codes (ADR 0025 D3). The transaction codes (ADR 0016 D3, I-14) and `ASSET_MISMATCH` (I-5) are renames in
   the table above, not additions.
7. `PERMISSION_DENIED` covers a missing scope and an unregistered or suspended tenant (ADR 0020). The message does
   not say which.
8. **Responses that may lack `LedgerErrorDetail`** (R-13); clients fall back to the status code: anything
   produced outside the service (proxies, load balancers, TLS failures, connection resets); gRPC statuses from the
   library or client (`UNIMPLEMENTED`, `RESOURCE_EXHAUSTED` for an oversized message, `DEADLINE_EXCEEDED`,
   `CANCELLED`); REST errors raised by the framework before the adapter (404 unknown path, 405, 415, 413). The
   adapter attaches a detail where the framework lets it; a test lists which ones it covers.
9. From `v1.0.0`, `ErrorCode` values are only appended. Before `v1.0.0` (draft, D3.1) the renames listed under D2
   are allowed. Clients treat an unknown value as "failed, not retryable unless the
   status is `UNAVAILABLE`, `ABORTED` or `RESOURCE_EXHAUSTED`" (D3).

### D3. Contract freeze, breaking-change baseline and client tolerance (old 0032)
1. **Draft until `v1.0.0`.** Until the first release tag, `ledger.v1` is a draft and may change in any way;
   `contracts/README.md` says so. `buf breaking` runs but does not block.
2. **The contract freezes at the tag `v1.0.0`.** Preconditions: the proto changes from ADRs 0014–0026 are
   applied, the first consumer has built against a release candidate, and these ADRs are accepted.
3. **From `v1.0.0`, `buf breaking` blocks** and compares against the latest release tag, not `main`. Rule set
   `FILE` stays. It also gates `ledger.events.v1` (ADR 0024 D5).
4. **Forbidden inside `ledger.v1` though `buf` passes them:** lowering a published limit, rejecting input that was
   accepted, changing a code's gRPC status, HTTP status or "recorded" flag, changing a default, changing the
   canonical hash encoding of an existing hash version (ADR 0018 D2).
5. **Clients must tolerate** unknown fields, unknown enum values (including `ErrorCode` and status enums), and
   errors without `LedgerErrorDetail`. The integration guide shows the parser settings for .NET and Java. The
   server stays strict on input (D1.4).
6. The contract artifact of each release carries its tag; consumers pin it (ADR 0012). It contains the `ledger.v1` and
   `ledger.events.v1` protos with their googleapis imports, and the generated OpenAPI document (REST only).
   `ledger.events.v1` is not in `contracts/proto` yet.

## Consequences
- Each inbound adapter maps proto messages to use-case commands (ADR 0026 D2). Limits and validation live in the
  application commands, and the conformance tests of D1.7 catch REST/gRPC drift.
- `ABORTED` now always means "retry the same call with the same key"; conflict no longer shares it, so a generic
  retry policy on `ABORTED` cannot loop on a conflict. Client retry policies must include `ABORTED` for ledger
  writes; safe because every write carries a key.
- A REST client that looks only at the status cannot tell `INVALID_ARGUMENT` from `FAILED_PRECONDITION`; branch on
  the error code. Every write and rejection carries `request_id` and `correlation_id` for audit (ADR 0013).
- If Spring gRPC ships transcoding later, the adapter can be replaced without a contract change.
- The protobuf JSON parser accepts a JSON number for a string or `int64` field; OpenAPI declares amounts as strings
  and the integration guide tells clients to send strings.
- `ledger-api-rest` gains `protobuf-java-util`; licence and version checked before it is added.
- The review fixes merge to `main` as normal changes. After `v1.0.0`, adding an `ErrorCode` value is allowed only
  because clients were told to tolerate it.
- Follow-ups: rename the error message, add the codes, remove `correlation_id` fields, regenerate OpenAPI.

## Needs benchmark or human verification
- Spike: Spring MVC message conversion for protobuf JSON on Spring Framework 7, and how the router treats `:` in a
  path (D1.6 avoids the second question).
- JSON parser behaviour of the first consumer (.NET) and Java on unknown fields and enum values.
- Run `cd contracts && buf breaking --against '../.git#branch=main,subdir=contracts'` on a Linux CI runner. Status on
  2026-11-15: buf 1.75.0 was installed on a Windows workstation. `buf lint` passed. `buf build
  '../.git#branch=main,subdir=contracts'` accepted that exact git input. `buf breaking` between image files behaved
  correctly (unchanged tree against `main`: exit 0; renamed enum value: exit 100). But `buf breaking --against
  '../.git#branch=main,subdir=contracts'` (and even `--against .`) exited 1 with no message on that Windows machine,
  so the literal command is not verified end to end. A Linux run is still needed (Docker was not permitted in that
  session).

- None beyond the verifications above.

## Alternatives rejected
- **Transcoding proxy in front of the gRPC port.** A mandatory extra component; it would terminate TLS in front of
  the service, against ADR 0020 D2; its errors carry no ledger detail.
- **Community transcoding library in the process.** A one-maintainer dependency in the money path.
- **Keep 422.** REST would differ from the standard mapping, and "REST" would again have two definitions.
- **REST-only DTOs with a JSON library.** A second schema; it drifts.
- **`CONTENTION` as `UNAVAILABLE` / 503.** Matches guideline (a) word for word, but 5xx on a hot account looks
  like an outage: proxies that eject hosts on consecutive 5xx would remove healthy instances (unverified for any
  specific proxy). `ABORTED`'s own text names "transaction abort".
- **Conflict stays `ABORTED`.** Under guideline (b) a client restarts with the same key and gets the same conflict.
- **`UNBALANCED_ENTRY` stays `FAILED_PRECONDITION`**; **`OUT_OF_RANGE` for `BALANCE_LIMIT_EXCEEDED`** (its text is
  about iterating past an end); **reject an invalid correlation id** (a tracing header should not fail a money write).
- **`buf breaking` against `main`, or freeze at first merge.** Freezes a draft by merging it.
- **Enums as strings or integers to avoid JSON parser failures.** Loses the schema; the tolerance rule is cheaper.
